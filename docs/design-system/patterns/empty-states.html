Empty and error states

When there is nothing to show, say why in one calm sentence and offer the one next step that helps.

Pattern
  • Overview
  • When to use
  • Structure
  • States
  • Responsive behaviour
  • Accessibility
  • Content
  • Do and don’t
  • Sources

Overview

Absence is a state of the page, not a failure of it. Keep the page around it (header, title, filters) and put a short, warm explanation where the content would have been, with one action that changes the situation. Different reasons for emptiness need different words and different actions, so name the reason.

SituationTitlePrimary action
First use: nothing created yetNo projects yetCreate a project
No results: search or filters exclude everythingNo notes match "harbour budget"Clear filters
All done: a queue that has been worked throughYou're all caught upnone, or a link back
Couldn't load: the request failedWe couldn't load your notesTry again
No access: the person can't see thisThis notebook is privateAsk for access
Gone: the page doesn't existWe can't find that pageGo to your home page

Use the empty state inside a page region and the error page when the whole route can't be shown.

When to use

  • A collection is empty on first use, after filtering, or after everything has been handled.
  • A region failed to load while the rest of the page is fine: show the error in that region only.
  • The whole route fails (not found, no access, server error, offline): use an error page inside the normal shell, so navigation still works.
  • Not for a single empty field or value; show an em dash or "Not set" in place, without a panel.

Structure

Inside the region: an icon tile, a title, one sentence of explanation, then one primary action and at most one quiet alternative. Keep the region's header and controls above it.

States

  • First use invites creation and explains, in one sentence, what the thing is for.
  • No results names the query or filters, says what was searched, and offers to clear them.
  • All done is calm and brief, with no call to action unless there is a real next thing.
  • Couldn't load keeps controls and context in place and offers Try again. After a second failure, add a way to report it.
  • No access explains who can see it and how to ask; never pretend the page is missing when it isn't.
  • Offline says what still works and that changes wait on the page until the connection returns.

Responsive behaviour

  • 360px: the panel spans the column with comfortable padding; actions wrap and may stack. Keep the icon tile small; never add a large illustration that pushes the action below the fold.
  • 768px: the message stays centred at a short measure (about 30rem) so lines stay easy to read.
  • 1024px and up: an empty region sits where the content would be, in the same column. Don't let it stretch across side columns. An error page aligns with the page's left edge like any page title.

Accessibility

Headings: the empty title is a real heading at the right level for its region, so it appears in the page outline.

Focus: don't move focus when a region turns out to be empty in the background. After a person clears filters or retries, keep focus on the control they used. On a full error route, focus moves to the page heading like any navigation.

Announcements: a result count that changes to zero lives in a role="status" region ("0 notes"). A region that fails after load uses role="alert" once.

Not colour alone: the error tile is tinted, but the title says what happened in words.

Decorative icons: aria-hidden="true". The error page's large code is hidden from assistive technology because the title already says it.

Content

  • Title: what is true now, in plain words: "No projects yet", "We couldn't load your notes". Not "Nothing here!" and not "Error 500".
  • Sentence: why, and what will make it change. One sentence, two at most.
  • Action: a verb and an object that fixes this exact situation: Create a project, Clear filters, Try again, Ask for access.
  • Reassure when something failed: "Nothing has been lost." Never blame the person or the network by name.
  • Error codes are for support, not for headlines; put them in small print if they help.
