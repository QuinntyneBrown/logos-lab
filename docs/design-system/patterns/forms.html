Forms

Ask for a clear answer, keep everything a person typed, and say what happens next.

Pattern
  • Overview
  • When to use
  • Structure
  • States
  • Responsive behaviour
  • Accessibility
  • Content
  • Do and don’t

Overview

A form is a short conversation: a few plain questions, one at a time, in the order a person would answer them. Every field has a visible label, help sits under the label it explains, and a single sage button moves the task forward. When something is wrong, the form says so once at the top in a linked error summary and again beside the field, and nothing the person typed is ever cleared.

When to use

  • Setting up and editing: creating an account, a project, a gathering or a profile.
  • Choosing preferences: notification settings, privacy and display options (often switches that save as they change).
  • A short decision inside a task: one or two fields belong in a dialog. Anything longer, or anything a person may want to come back to, gets its own screen.

Do not put editable fields inline in a read-only page. A button such as Edit details opens a dialog or navigates to an edit screen; the page itself stays calm and readable.

Structure

Build every form from the same parts, top to bottom:

  1. Title and one-line lead — what this form is for and who will see the answers.
  2. Error summary — only after a failed submit; a linked list of every problem.
  3. Sections — a fieldset.form-section with a legend for each group of related questions.
  4. Fields — label, optional marker, help, control, error, in that order. Short related answers (first and last name, start and end time) may share a .field-row.
  5. Actions — .form-actions at the end: the safe action first, then the one primary action.

States

A form moves through default → invalid → submitting → saved, or failed with everything kept.

  • Default: no errors are shown before a person has answered. Required fields are the norm; mark the exceptions (optional).
  • Invalid: validate a field when the person leaves it, and re-check it as they type once it has shown an error, so the message disappears the moment it is fixed. On submit, show the summary and move focus to it.
  • Submitting: the primary button keeps its width, adds a spinner and says what is happening (Saving…). Fields stay readable; Cancel stays available until the request is sent.
  • Saved: a toast confirms a change on the same page; a new screen confirms a created object by showing it.
  • Failed: say what happened, keep every answer, and offer Try again.

Responsive behaviour

  • 360px: one column. Every field, row and action stacks; the primary action may become btn--block at the end of the form. Keep labels above inputs, never beside them.
  • 768px: .field-row pairs short, related answers side by side. A description textarea stays full width.
  • 1024px and up: keep forms to a readable measure (.narrow, about 40rem) even on a wide screen, and let a summary or help card sit in the side column of a .two-col layout.

.form-card pads more generously from 640px. Long labels, help and error text wrap; nothing truncates.

Accessibility

Labels: every control has a visible <label for>, or a fieldset with a legend for a group of radios, checkboxes or switches. Placeholder text is never the label.

Help and errors: connect both with aria-describedby (help first, then the error). Set aria-invalid="true" only on fields that are actually wrong, and only after the person has answered or submitted.

Error summary: on a failed submit, focus the summary (tabindex="-1", role="alert"). Each item is a link to its field, with the same words as the inline error.

Busy: while submitting, set aria-busy="true" on the form and on the pressed button; keep its label so screen readers still announce Saving… rather than an unnamed spinner. Don't disable every field.

Keyboard: native tab order follows the visual order. Enter submits from a single-line field; never submit on change of a select.

Autocomplete: use autocomplete tokens (name, email, new-password) and the right type so phones show the right keyboard.

Content

  • Labels are short nouns in sentence case: Full name, Email, Project name. No colons, no "Please enter".
  • Help answers the question a person is about to ask: who sees this, how long it can be, what format. "Everyone on Northwind can see this."
  • Errors say what to do, not what went wrong: "Enter a date after today", not "Invalid date". Never blame: avoid "You forgot" and "wrong".
  • Optional fields say (optional); required is the default and needs no asterisk.
  • Buttons name the result: Create project, Save changes, Send invitation. Not "Submit".
