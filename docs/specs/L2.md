# L2 - Detailed Requirements

Each requirement traces to exactly one L1 in `L1.md`. Acceptance criteria are written in
Given/When/Then form and translate directly into acceptance tests. Every acceptance test file must
carry a header naming the L2 requirement(s) it covers, for example:

```typescript
// Acceptance Test
// Traces to: L2-027, L2-030
// Description: Learner enrols in a course and sees progress update after completing a lesson
```

**Conventions used below**

- *Content* means any course, learning module, video, article, collection or event.
- *Published* means content whose workflow state is Published and whose publish time has passed.
- Viewport classes: XS <576px, SM >=576px, MD >=768px, LG >=992px, XL >=1200px.
- Performance figures are measured in production-like infrastructure with production-sized seed data.
- All times are stored in UTC and displayed in the viewer's time zone, with the zone named.

## L2-001: Home page
**Traces to:** L1-001

The home page (`/`) must present featured content, the newest published content, upcoming events
and featured experts, and must give every visitor a direct path to search and to the catalogue.

**Acceptance Criteria:**
1. Given an editor has featured up to 6 items, when anyone opens `/`, then those items appear in the
   featured section in the order the editor set.
2. Given published content exists, when anyone opens `/`, then the "Latest" section shows the 8 most
   recently published items across all content types, newest first.
3. Given events exist with a start time in the future, when anyone opens `/`, then the "Upcoming
   events" section shows the next 3 published events by start time, and no past or draft events.
4. Given no upcoming events exist, when anyone opens `/`, then the events section is replaced by an
   empty state that links to past event recordings.
5. Given a signed-in learner has at least one course in progress, when they open `/`, then a
   "Continue learning" strip shows up to 3 in-progress items, most recently accessed first.
6. Given a draft, scheduled or archived item, when anyone opens `/`, then that item does not appear
   anywhere on the page.

## L2-002: Catalogue browsing and filtering
**Traces to:** L1-001

The catalogue (`/explore`) must list all published content and must let users filter and sort it.
Filter state must be reflected in the URL so that it can be shared and bookmarked.

**Acceptance Criteria:**
1. Given published content of every type, when a user opens `/explore`, then the results show 24
   items per page, sorted by "Newest", each as a card with type, title, contributor, topic and
   duration or date.
2. Given the user selects type "Video" and topic "AI ethics", when the results update, then only
   published videos tagged "AI ethics" are shown and the URL contains `type=video&topic=ai-ethics`.
3. Given a user opens a URL that contains valid filter parameters, when the page loads, then the
   filters are pre-applied and the controls show the selected values.
4. Given a URL with an unknown filter value (for example `type=podcast`), when the page loads, then
   the unknown value is ignored, the remaining filters apply, and no error is shown.
5. Given filters that match nothing, when the results update, then an empty state names the active
   filters and offers a single "Clear filters" action.
6. Given the sort is changed to "Most popular", when the results update, then items are ordered by
   the number of distinct members who engaged with them in the last 30 days, descending.
7. Given filters for level (Introductory, Intermediate, Advanced), contributor (an expert or Logos
   Lab) and duration (<15 min, 15-60 min, >60 min), when each is applied, then results match it.

## L2-003: Site-wide search
**Traces to:** L1-001

A search field must be available from the global header on every public page. Search must cover
titles, summaries, body text, transcripts, topics and expert names across all published content.

**Acceptance Criteria:**
1. Given a video whose transcript contains "imago Dei", when a user searches "imago dei", then the
   video appears in the results (matching is case-insensitive and accent-insensitive).
2. Given a search query, when results are returned, then they are grouped by content type with a count
   per type, and the user can narrow to a single type.
3. Given a query with a misspelling within an edit distance of 2 of an indexed term (for example
   "theolgy"), when the search returns no exact matches, then results for the corrected term are
   shown with the notice "Showing results for theology".
4. Given a query that matches nothing, when results are returned, then a no-results state shows
   the query, suggests browsing the 5 most popular topics, and links to the catalogue.
5. Given draft, scheduled, archived or moderator-hidden content matches a query, when anyone
   searches, then that content is not returned.
6. Given a query, when results are shown, then the matching terms are highlighted in each result
   snippet, and the highlight markup is generated by the application, never taken from user input.

## L2-004: Search input handling and performance
**Traces to:** L1-001

Search must validate its input and must respond quickly enough to support type-ahead suggestions.

**Acceptance Criteria:**
1. Given a query shorter than 2 characters after trimming, when the user submits, then no request is
   sent and the field shows "Enter at least 2 characters".
2. Given a query longer than 200 characters, when it reaches the API, then the API responds with
   400 and a validation message, and the UI prevents typing beyond 200 characters.
3. Given a query containing SQL or HTML metacharacters (for example `'; DROP TABLE` or `<script>`),
   when it is submitted, then it is treated as literal text, results render safely, and no error
   occurs.
4. Given the user types in the header search field, when 250 ms pass without a keystroke and the
   query has at least 2 characters, then up to 6 suggestions appear.
5. Given 200 concurrent searches against the production-sized index, when the search API responds,
   then the p95 latency is 400 ms or less.
6. Given one client sends more than 60 search requests in a minute, when the next request
   arrives, then the API responds with 429 and a `Retry-After` header.

## L2-005: Topic pages
**Traces to:** L1-001

Every topic in the controlled taxonomy must have a public page (`/topics/{slug}`) listing its
published content and the experts associated with it.

**Acceptance Criteria:**
1. Given the topic "Theology of technology" exists, when anyone opens `/topics/theology-of-technology`,
   then the page shows the topic's name and description, its published content (newest first, 24
   per page) and the experts who have published content in it.
2. Given a topic slug that does not exist, when it is requested, then the page returns HTTP 404 and
   the not-found page.
3. Given a topic that has no published content, when its page is opened, then an empty state is shown
   and the topic is not listed in the catalogue topic filter.
4. Given a content card on any page, when the user activates one of its topic tags, then they are
   taken to that topic's page.

## L2-006: Registration
**Traces to:** L1-002

Visitors must be able to create an account with an email address and a password.

**Acceptance Criteria:**
1. Given a visitor submits a unique, well-formed email address, a display name of 2-50 characters,
   a valid password and acceptance of the Terms and Privacy Policy, when they register, then the
   account is created in the "Unverified" state with the Learner role and a verification email is
   sent.
2. Given a password shorter than 12 characters or longer than 128 characters, when the form is
   submitted, then registration is refused with a message stating the length rule.
3. Given a password that appears in the platform's known-breached password list, when the form is
   submitted, then registration is refused with "This password has appeared in a data breach.
   Choose a different one."
4. Given an email address that already has an account, when a visitor registers with it, then the
   response and the UI are the same as for a new address, and the existing account owner receives
   an email saying someone tried to register with their address. Account existence is never
   revealed.
5. Given the Terms and Privacy Policy checkbox is not checked, when the form is submitted, then
   registration is refused and the checkbox is marked invalid.
6. Given the marketing-email consent checkbox, when the registration form first renders, then it is
   unchecked, and leaving it unchecked does not block registration.
7. Given more than 5 registration attempts from one IP address in 10 minutes, when another attempt
   is made, then the API responds with 429.

## L2-007: Email verification
**Traces to:** L1-002

A new account must verify its email address before it can contribute anything (enrol, comment,
register for events, message).

**Acceptance Criteria:**
1. Given an unverified account, when its owner opens the verification link within 24 hours, then the
   account becomes "Active" and the link can never be used again.
2. Given a verification link older than 24 hours or already used, when it is opened, then the page
   says the link has expired and offers to send a new one.
3. Given an unverified account, when its owner signs in, then they can browse but every
   contribution action shows a prompt to verify, with a "Resend email" button.
4. Given "Resend email" is pressed, when fewer than 60 seconds have passed since the last email,
   then the button is disabled and shows the seconds remaining, and no more than 5 emails are
   sent per account per 24 hours.
5. Given an account unverified for 30 days, when the nightly cleanup job runs, then the account and
   its personal data are deleted.

## L2-008: Sign in
**Traces to:** L1-002

Members must be able to sign in with their email address and password.

**Acceptance Criteria:**
1. Given an Active account and correct credentials, when the member signs in, then a session is
   created and they are returned to the page they were on, or to `/dashboard` if they came from the
   sign-in page directly.
2. Given an incorrect password or an unknown email address, when sign-in is attempted, then the
   message "Email or password is incorrect" is shown in both cases, and the response time differs
   by no more than 50 ms between the two cases at p95.
3. Given a `returnUrl` parameter that points to another origin (for example
   `returnUrl=https://evil.example`), when sign-in succeeds, then the member is sent to `/dashboard`
   and not to the external URL.
4. Given a Suspended or Deactivated account, when its owner enters correct credentials, then
   sign-in is refused with a message explaining the account status and how to contact support.
5. Given a role that requires multi-factor authentication (L2-014), when the password step
   succeeds, then a session is created only after a valid second factor is provided.

## L2-009: Brute-force protection
**Traces to:** L1-002

Sign-in, password reset and verification endpoints must resist credential stuffing and brute
force attacks.

**Acceptance Criteria:**
1. Given 5 failed sign-in attempts for one account within 15 minutes, when a sixth attempt is made,
   then it is refused for 15 minutes regardless of password correctness, the generic error is
   shown, and the account owner is emailed about the failed attempts.
2. Given 20 failed sign-in attempts from one IP address across any accounts within 15 minutes, when
   another attempt arrives from that IP, then the API responds with 429 for 15 minutes.
3. Given a lockout has expired, when the correct credentials are entered, then sign-in succeeds and
   the failure counter resets.
4. Given any lockout or throttle event, when it occurs, then a security event is logged with the
   account identifier, the IP address and a timestamp, but never the submitted password.

## L2-010: Sessions and sign out
**Traces to:** L1-002

Sessions must be secure, must expire, and must be revocable by the member.

**Acceptance Criteria:**
1. Given a signed-in Learner or Expert, when 14 days pass with no activity, or 30 days pass since
   sign-in, then the session expires and the next request requires signing in again.
2. Given a signed-in Editor, Moderator or Administrator, when 30 minutes pass with no activity, or
   12 hours pass since sign-in, then the session expires.
3. Given a signed-in member, when they choose "Sign out", then the session is invalidated on the
   server, the session cookie is cleared, and pressing Back does not reveal authenticated pages.
4. Given a member opens Account > Sessions, when the page loads, then it lists every active session
   with device type, browser, approximate location (city) and last activity, marking the current
   session.
5. Given a member chooses "Sign out of all other sessions", when they confirm, then every session
   except the current one is invalidated within 5 seconds.
6. Given a member changes their password or email address, when the change succeeds, then every
   other session is invalidated.

## L2-011: Password reset
**Traces to:** L1-002

Members who forget their password must be able to reset it through their verified email address.

**Acceptance Criteria:**
1. Given any email address is submitted to "Forgot password", when the request completes, then the
   UI shows "If an account exists for that address, we've sent a reset link" whether or not an
   account exists.
2. Given an Active account, when a reset is requested, then an email is sent with a single-use link
   that expires after 60 minutes, and any earlier unused reset links for that account are
   invalidated.
3. Given a valid reset link, when a new password that meets L2-006 rules is submitted, then the
   password is changed, all sessions are invalidated, and a confirmation email is sent.
4. Given an expired, used or tampered reset link, when it is opened, then the page explains that the
   link is invalid and offers to request a new one.
5. Given more than 3 reset requests for one email address within an hour, when another arrives,
   then no further email is sent and the UI response is unchanged.

## L2-012: Change password and email
**Traces to:** L1-002

Members must be able to change their password and email address after confirming their identity.

**Acceptance Criteria:**
1. Given a signed-in member, when they change their password, then they must enter their current
   password, and the new password must meet L2-006 rules and must differ from the current one.
2. Given a member requests an email change, when they submit a new address and their current
   password, then a verification link is sent to the new address, and the email does not change
   until that link is opened within 24 hours.
3. Given the email change is confirmed, when it completes, then a notice is sent to the old address
   with a link to report that the change was not authorized.
4. Given the new address already belongs to another account, when the change is requested, then the
   UI shows the same response as for a free address and no change occurs.

## L2-013: Member profile
**Traces to:** L1-002

Members must be able to manage their display name, avatar, short bio and visibility.

**Acceptance Criteria:**
1. Given a signed-in member, when they open Profile settings, then they can edit display name (2-50
   characters), bio (up to 500 characters) and avatar.
2. Given an avatar upload, when the file is JPEG, PNG or WebP, 5 MB or smaller, and at least
   128x128 pixels, then it is accepted, cropped to a square, re-encoded, and stripped of EXIF
   metadata. Any other file is refused with a message stating the rules.
3. Given a member's profile, when another member views it, then only display name, avatar, bio and
   public community activity are shown. Email address, enrolments and progress are never shown.
4. Given a display name containing HTML or script, when it is displayed anywhere, then it is
   rendered as literal text.

## L2-014: Multi-factor authentication
**Traces to:** L1-002

Members must be able to enable time-based one-time-password (TOTP) multi-factor authentication. It
is mandatory for the Expert, Editor, Moderator and Administrator roles.

**Acceptance Criteria:**
1. Given a member enables MFA, when they scan the QR code and enter a valid 6-digit TOTP code, then
   MFA is enabled and 10 single-use recovery codes are shown once.
2. Given a user is granted the Expert, Editor, Moderator or Administrator role without MFA enabled,
   when they next sign in, then they must enrol in MFA before reaching any page.
3. Given MFA is enabled, when a wrong TOTP code is entered 5 times in 15 minutes, then the second
   factor step is locked for 15 minutes.
4. Given a recovery code is used, when sign-in completes, then that code can never be used again and
   the member is emailed that a recovery code was used.
5. Given a member disables MFA, when they confirm with a current TOTP code and their password, then
   MFA is disabled. Members of roles where MFA is mandatory cannot disable it.

## L2-015: Anonymous access boundaries
**Traces to:** L1-003

Visitors must be able to explore the platform without an account, but learning activity must
require one.

**Acceptance Criteria:**
1. Given a visitor, when they open the home page, catalogue, search, topic pages, expert profiles,
   article pages, collection pages, event pages, or the overview page of a course, module or video,
   then the page loads without a sign-in prompt.
2. Given a visitor, when they play a video, launch a module, enrol in a course, open a lesson,
   register for an event, comment, save an item or follow anything, then they are prompted to sign
   in or register, and they are returned to the same action afterwards.
3. Given a video an editor has marked "Public preview", when a visitor plays it, then it plays
   without sign-in.
4. Given an unauthenticated request to an API endpoint that is not explicitly anonymous, when it is
   received, then the API responds with 401 and no data.

## L2-016: Role permissions
**Traces to:** L1-003

Every API endpoint must enforce role-based permissions on the server. Permissions are cumulative:
every role also holds the Learner permissions.

| Capability | Learner | Expert | Editor | Moderator | Admin |
|---|---|---|---|---|---|
| Learn, comment, message, register for events | yes | yes | yes | yes | yes |
| Author own content, edit own expert profile | - | yes | yes | - | - |
| Lead own cohorts | - | yes | yes | - | - |
| Review, publish, schedule, archive any content | - | - | yes | - | yes |
| Curate featured content and collections as Logos Lab | - | - | yes | - | yes |
| Handle reports, hide or remove content, suspend users | - | - | - | yes | yes |
| Manage users, roles, invitations, taxonomy, settings | - | - | - | - | yes |
| View platform-wide analytics | - | - | yes | - | yes |

**Acceptance Criteria:**
1. Given each row of the table, when a user without that capability calls the corresponding API
   endpoint, then the API responds with 403, and the attempt is logged as a security event.
2. Given a user without a capability, when they navigate to a page that requires it, then they see
   the "You don't have access to this page" state, and the navigation never shows links to it.
3. Given an Administrator, when they call any endpoint in the table, then the call is permitted.
4. Given the UI hides a control, when the API is called directly without the capability, then the
   API still refuses it. The UI is never the only enforcement.

## L2-017: Ownership scoping
**Traces to:** L1-003

User-owned data must be scoped to its owner. Resources must never be exposed to other users
through guessable identifiers (IDOR).

**Acceptance Criteria:**
1. Given learner A, when A requests learner B's progress, saved items, notifications, enrolments,
   certificates-in-progress, messages or account data by ID, then the API responds with 404 and
   reveals nothing about whether the resource exists.
2. Given expert A, when A requests to edit or submit expert B's draft, then the API responds with
   404.
3. Given a list endpoint (for example `/api/me/saved`), when it is called, then it returns only the
   caller's records, and no query parameter can widen the scope to another user.
4. Given any resource identifier exposed in a URL or API response, when it is generated, then it is
   a non-sequential identifier (UUID or slug), never an auto-increment integer.

## L2-018: Role changes
**Traces to:** L1-003

Changes to a user's roles must take effect immediately and must be auditable.

**Acceptance Criteria:**
1. Given an Administrator removes a role from a signed-in user, when that user makes their next
   request, then the removed capabilities are refused without the user having to sign in again.
2. Given any role is granted or removed, when the change is saved, then an audit entry records the
   actor, target user, role, old value, new value and timestamp.
3. Given an Administrator, when they try to remove the Administrator role from the last remaining
   Administrator, then the change is refused with an explanation.
4. Given a user is granted a role, when the change is saved, then the user receives an in-app and an
   email notification naming the role.

## L2-019: Account states
**Traces to:** L1-003

Accounts must have one of these states: Unverified, Active, Suspended (until a date), Banned or
Deactivated. Each state determines what the account can do.

**Acceptance Criteria:**
1. Given a Suspended account, when the suspension end date passes, then the account returns to
   Active automatically and its owner is notified.
2. Given an account is Suspended or Banned, when the state changes, then all of its sessions are
   invalidated within 5 seconds.
3. Given a Banned account, when its content is viewed, then its comments remain hidden and its
   display name is shown as "Removed member".
4. Given a Deactivated account (self-initiated, L2-117), when other members view its past comments,
   then they are attributed to "Former member".

## L2-020: Expert invitation and onboarding
**Traces to:** L1-004

Experts join by invitation only. Administrators invite experts by email, and the invited expert
completes their profile before their first content can be submitted.

**Acceptance Criteria:**
1. Given an Administrator enters an email address and name and sends an invitation, when it is
   sent, then the invitee receives an email with a single-use link that expires after 14 days.
2. Given an invitation link, when the invitee opens it, then they can sign in to an existing
   account or create one, and on completion the Expert role is granted and MFA enrolment
   (L2-014) is required.
3. Given a new expert, when they first open the authoring workspace, then they are guided to complete
   the required profile fields (photo, professional title, bio of 100-2,000 characters, at least one
   area of expertise), and they cannot submit content until those fields are complete.
4. Given an Administrator revokes an unaccepted invitation, when the invitee opens the link, then
   it is shown as no longer valid.
5. Given the list of invitations, when an Administrator views it, then each shows status (Pending,
   Accepted, Expired, Revoked), the inviter and the dates.

## L2-021: Public expert profile
**Traces to:** L1-004

Each expert has a public profile at `/experts/{slug}`.

**Acceptance Criteria:**
1. Given an expert with a completed profile, when anyone opens their profile, then it shows photo
   (with alt text set to the expert's name), name, professional title, affiliation, bio, areas of
   expertise, and up to 5 external links.
2. Given the expert has published content, when the profile is shown, then their content is listed
   in tabs by type (Courses, Modules, Videos, Articles, Collections, Events), showing only tabs that
   have items, with a count on each.
3. Given an external link on a profile, when it is saved, then it must be an `https://` URL. When it
   is rendered, it opens in a new tab with `rel="noopener noreferrer"` and is identified as external
   to assistive technology.
4. Given an expert whose Expert role has been removed, when their profile URL is opened, then it
   returns 404, and their past published content remains attributed to them with no profile link.
5. Given an expert's bio, when it is rendered, then only the permitted formatting (paragraphs, bold,
   italic, links) is kept and any other markup is removed.

## L2-022: Experts directory
**Traces to:** L1-004

A public directory at `/experts` lists every expert who has a completed profile.

**Acceptance Criteria:**
1. Given experts exist, when anyone opens `/experts`, then experts are shown alphabetically by
   surname, 24 per page, each with photo, name, title and their number of published items.
2. Given the topic filter is set, when results update, then only experts with that area of
   expertise or published content in that topic are shown.
3. Given a name search of at least 2 characters, when it is submitted, then experts whose name
   contains the text (case- and accent-insensitive) are shown.

## L2-023: Expert self-service profile editing
**Traces to:** L1-004

Experts must be able to edit their own public profile. Profile changes go live immediately and are
logged so that editors can review them afterwards.

**Acceptance Criteria:**
1. Given an expert edits and saves their profile, when the save succeeds, then the public profile
   shows the change within 60 seconds.
2. Given a profile change, when it is saved, then an audit entry records the changed fields with
   their old and new values, and editors receive an in-app notification.
3. Given an editor, when they view an expert's profile history, then they can restore any earlier
   version, and the expert is notified of the restoration.
4. Given an expert tries to change another expert's profile through the API, when the request is
   received, then it is refused with 404.

## L2-024: Follow an expert
**Traces to:** L1-004

Members must be able to follow experts to be notified when they publish new content or announce
events.

**Acceptance Criteria:**
1. Given a signed-in member on an expert's profile, when they press "Follow", then the button changes
   to "Following" with `aria-pressed="true"`, and the expert's follower count increases by 1.
2. Given a member follows an expert, when that expert's content is published or an event they host
   is published, then the member receives a notification according to their preferences (L2-093).
3. Given a member is following an expert, when they press "Following" and then confirm "Unfollow",
   then the follow is removed and no further notifications are sent.
4. Given a member, when they follow and unfollow the same expert more than 10 times in a minute,
   then further requests are refused with 429.

## L2-025: Course overview page
**Traces to:** L1-005

Each course has a public overview page at `/courses/{slug}`.

**Acceptance Criteria:**
1. Given a published course, when anyone opens its overview, then it shows title, summary, cover image,
   contributor (one or more experts, or Logos Lab), level, estimated total duration, learning outcomes
   (3-8 items), topics, the syllabus of sections and lessons with each lesson's type and duration,
   and the number of enrolled learners.
2. Given a visitor or a non-enrolled member, when they view the syllabus, then lesson titles are
   visible but lessons cannot be opened.
3. Given an enrolled learner, when they view the overview, then the primary action is "Continue",
   which opens the first incomplete lesson, and their progress percentage is shown.
4. Given a course has an active cohort the learner belongs to, when they view the overview, then a
   link to the cohort space is shown (L2-064).
5. Given a course is archived, when an enrolled learner opens it, then a notice says it is no
   longer maintained and they can still finish it. Non-enrolled users get 404.

## L2-026: Course structure
**Traces to:** L1-005

A course is made of 1-20 ordered sections, each with 1-30 ordered lessons. Each lesson is one of these
types: Video, Article, Learning module (SCORM) or Text. A lesson is either required or optional.

**Acceptance Criteria:**
1. Given an author builds a course, when they save it, then sections and lessons keep the order the
   author set, and reordering by drag or keyboard (move up/down) persists.
2. Given a course with no sections or a section with no lessons, when it is submitted for review,
   then submission is refused with a message naming each empty section.
3. Given a lesson references an existing video, article or module, when that item is updated and the
   update is published, then the course lesson shows the updated item.
4. Given a course lesson references an item, when an editor tries to archive that item, then they
   are warned which published courses use it and must confirm.
5. Given a course, when its estimated duration is calculated, then it equals the sum of its lesson
   durations rounded to the nearest 5 minutes.

## L2-027: Enrolment
**Traces to:** L1-005

Verified members must be able to enrol in and leave courses.

**Acceptance Criteria:**
1. Given a verified member on a published course overview, when they press "Enrol", then an enrolment
   is created, they are taken to the first lesson, and the course appears in their dashboard.
2. Given a member is already enrolled, when an enrolment request is repeated, then no duplicate
   enrolment is created and the API returns the existing enrolment.
3. Given an enrolled learner chooses "Leave course" and confirms in a dialog, when the action
   completes, then the course is removed from their in-progress list, and their progress is
   kept so that re-enrolling within 12 months restores it.
4. Given an unverified member, when they press "Enrol", then they are prompted to verify their email
   (L2-007) and no enrolment is created.

## L2-028: Lesson player and navigation
**Traces to:** L1-005

Enrolled learners study lessons in a lesson player with course navigation.

**Acceptance Criteria:**
1. Given an enrolled learner opens a lesson, when the page loads, then it shows the lesson content, the
   course outline with completion state per lesson, and "Previous" and "Next" controls.
2. Given a course with navigation set to "Sequential", when a learner tries to open a lesson that
   comes after an incomplete required lesson, then it is shown as locked with the reason, and a
   direct URL request is refused by the API with 403.
3. Given a course with navigation set to "Free" (the default), when a learner opens any lesson, then
   it opens regardless of completion state.
4. Given viewport XS or SM, when the lesson player is shown, then the course outline is collapsed
   behind an "Outline" button that opens it as a drawer, and the lesson content uses the full width.
5. Given a learner who is not enrolled, when they request a lesson URL, then they are redirected to
   the course overview.

## L2-029: Lesson completion rules

## L2-033: SCORM package upload and validation
**Traces to:** L1-006

Experts and editors must be able to upload SCORM 1.2 and SCORM 2004 (3rd and 4th edition) packages.
Each package is validated before it can be used.

**Acceptance Criteria:**
1. Given a `.zip` file of 500 MB or less with a valid `imsmanifest.xml` at its root, when it is uploaded,
   then the package is accepted, its SCORM version and launch resource are detected, and it is
   available to attach to a module within 2 minutes.
2. Given a file larger than 500 MB, not a zip archive, or missing `imsmanifest.xml`, when it is
   uploaded, then it is refused with a message stating which rule failed.
3. Given a zip containing entries with absolute paths or `..` segments (zip-slip), when it is
   processed, then the whole package is refused and a security event is logged.
4. Given a zip whose uncompressed size is over 2 GB or that contains more than 10,000 entries,
   when it is processed, then it is refused as a suspected zip bomb.
5. Given a package, when it is processed, then every file is scanned for malware, and any detection
   causes the package to be refused.
6. Given an upload is in progress, when the author views it, then a progress indicator shows percent
   uploaded and the processing state (Uploading, Validating, Scanning, Ready, Failed).

## L2-034: SCORM content isolation
**Traces to:** L1-006

SCORM content is untrusted third-party HTML and JavaScript. It must run isolated from the main
application.

**Acceptance Criteria:**
1. Given a launched module, when its content loads, then it is served from a separate content origin
   that is not a subdomain sharing cookies with `www.logoslab.ca`, so it cannot read the
   application's cookies or storage.
2. Given the module iframe, when it is rendered, then it uses a `sandbox` attribute that allows only
   scripts, forms, same-origin (for the content origin) and fullscreen.
3. Given module content, when it is requested from the content origin, then the request is
   authorized by a short-lived signed URL (valid 4 hours) issued only to signed-in learners who are
   eligible to launch it.
4. Given the module calls the SCORM API, when calls cross between the content origin and the
   application, then they pass through the Tessera scorm-player's message bridge, which accepts
   messages only from the expected origin.

## L2-036: SCORM runtime data and resume
**Traces to:** L1-006

The platform must implement the SCORM run-time data model needed for tracking and resume, and must
persist it on the server.

**Acceptance Criteria:**
1. Given a SCORM 1.2 module, when it calls `LMSSetValue` for `cmi.core.lesson_location`,
   `cmi.suspend_data`, `cmi.core.lesson_status` or `cmi.core.score.raw` and then `LMSCommit`,
   then the values are persisted and returned by `LMSGetValue` in the next session.
2. Given a SCORM 2004 module, when it sets `cmi.location`, `cmi.suspend_data`,
   `cmi.completion_status`, `cmi.success_status` or `cmi.score.scaled` and commits, then the values
   are persisted and returned in the next session.
3. Given a module that does not call commit, when 30 seconds pass with changed values, or the page
   is hidden or unloaded, then the player commits the pending values.
4. Given `suspend_data` longer than the SCORM limit for the version (4,096 characters for 1.2;
   64,000 for 2004 4th edition), when it is set, then the call returns the standard SCORM error
   code and the stored value is unchanged.
5. Given the network is unavailable during a commit, when connectivity returns, then queued values
   are sent in order, and no data is lost if the learner stays on the page.

## L2-076: Editorial workflow states
**Traces to:** L1-013

Every content item moves through defined workflow states with enforced transitions.

| From | To | Who |
|---|---|---|
| Draft | In review | Owner (expert) or editor |
| In review | Changes requested | Editor |
| In review | Approved | Editor (not the item's author) |
| Changes requested | In review | Owner or editor |
| Approved | Scheduled or Published | Editor |
| Scheduled | Published | System, at the scheduled time |
| Scheduled | Approved | Editor (unschedule) |
| Published | Archived | Editor |
| Archived | Published | Editor |

**Acceptance Criteria:**
1. Given each transition in the table, when it is performed by the stated role, then it succeeds and
   is recorded with actor, timestamp and optional comment.
2. Given any transition not in the table (for example Draft to Published), when it is attempted
   through the API, then it is refused with 409 and the current state is returned.
3. Given an editor who authored an item, when they try to approve it, then approval is refused. A
   different editor must approve it.
4. Given an item, when anyone with access views its history, then every transition is listed in
   order.

   appear. Cohort leaders see individual progress only for their own cohort members (L2-064).
3. Given product analytics events, when they are collected, then they contain no email address,

## L2-104: Transport security and security headers
**Traces to:** L1-018

All traffic must be encrypted, and every response must carry protective security headers.

**Acceptance Criteria:**
1. Given any request over plain HTTP, when it reaches the edge, then it is redirected (301) to HTTPS.
   TLS 1.2 is the minimum version, and TLS 1.0 and 1.1 handshakes fail.
2. Given any HTML response, when it is returned, then it includes
   `Strict-Transport-Security: max-age=31536000; includeSubDomains; preload`, a Content Security
   Policy without `unsafe-inline` or `unsafe-eval` for scripts, `X-Content-Type-Options: nosniff`,
   `Referrer-Policy: strict-origin-when-cross-origin`, a `Permissions-Policy` that denies unused
   features, and `frame-ancestors 'none'` (except the SCORM content origin, which allows only the
   application origin).
3. Given the production site, when it is scanned with Mozilla Observatory, then it scores A or higher.
4. Given the API, when a cross-origin request arrives from an origin that is not on the allow-list,
   then CORS headers are not returned, so the browser blocks it.

## L2-105: Input validation and output encoding
**Traces to:** L1-018

All input must be validated on the server, and all output must be encoded for its context.

**Acceptance Criteria:**
1. Given any API endpoint, when it receives a body, query or path value that fails its schema (type,
   length, format, range or enumeration), then it responds with 400 and field-level errors, and does
   not process the request.
2. Given the API, when it receives unknown properties in a JSON body, then they are ignored and never
   bound to persisted fields (mass-assignment protection). For example, a learner sending `"roles":
   ["Administrator"]` to the profile endpoint changes nothing.
3. Given any database access, when user input is used, then it is passed as a parameter, never
   concatenated into SQL. A test suite of SQL injection payloads against every search and filter
   endpoint returns no errors and no extra data.
4. Given user-supplied text, when it is rendered in HTML, attributes, URLs or JavaScript contexts, then
   it is encoded for that context. A test suite of XSS payloads in every user-text field executes no
   script.
5. Given any server-side request to a URL supplied by a user (for example link previews), when it is
   made, then requests to private, loopback, link-local and cloud metadata addresses are refused
   (SSRF protection).

## L2-106: Session cookies and CSRF protection
**Traces to:** L1-018

Session credentials must be protected from theft and cross-site request forgery.

**Acceptance Criteria:**
1. Given a session is created, when its cookie is set, then it is `HttpOnly`, `Secure`,
   `SameSite=Lax`, uses the `__Host-` prefix, and holds an opaque, random identifier of at least 128
   bits. No session token is stored in `localStorage` or `sessionStorage`.
2. Given a state-changing request (POST, PUT, PATCH, DELETE), when it lacks a valid anti-CSRF token or
   comes from a disallowed origin, then it is refused with 403.
3. Given a successful sign-in or privilege change, when it completes, then the session identifier is
   rotated (session fixation protection).

## L2-107: Rate limiting and abuse protection
**Traces to:** L1-018

The API must limit request rates to protect availability and prevent abuse.

**Acceptance Criteria:**

   (anonymous), then further requests receive 429 with a `Retry-After` header until the window resets.
2. Given endpoints with specific limits (sign-in, registration, password reset, search, comments,
   messages, reports, certificate verification), when they are called, then their specific limits in
   this document apply in addition to the global limit.
3. Given traffic that matches known bad-bot signatures or volumetric attack patterns, when it reaches
   the edge, then it is blocked by the web application firewall before reaching the application.

## L2-108: File upload security
**Traces to:** L1-018

Every uploaded file must be treated as untrusted.

**Acceptance Criteria:**
1. Given any uploaded file, when it is received, then its type is determined from its content (magic
   bytes), not from its extension or the declared MIME type, and a mismatch is refused.
2. Given any uploaded file, when it is stored, then it is scanned for malware before it becomes
   available, and infected files are quarantined and the uploader notified.
3. Given uploaded files, when they are stored, then they are stored with generated names in private
   storage outside the web root, and served only through the CDN with `Content-Disposition` and
   `Content-Type` headers set by the platform.
4. Given an upload request, when its size exceeds the type's limit, then it is refused before the
   whole body is read.

   separate, explicit pipeline step before the new version receives traffic.
3. Given a migration, when it is written, then it is backward compatible with the currently deployed
   version (expand and contract), so that deployment requires no downtime.
4. Given a failed production deployment, when health checks fail, then traffic automatically returns to
   the previous version within 10 minutes.
5. Given seed data, when the seed command runs more than once, then the result is identical to running
   it once.

---

## L2-140: Background jobs
**Traces to:** L1-023

Background work (media processing, emails, reminders, scheduled publishing, exports, retention) must
be reliable.

**Acceptance Criteria:**
1. Given any job, when it is executed more than once for the same input, then the outcome is the same as
   running it once (idempotent).
2. Given a job fails transiently, when it is retried, then it is retried with exponential backoff up to
   5 times, and then moved to a dead-letter queue that alerts the on-call channel.
3. Given a deployment, when running jobs are interrupted, then they resume or restart without data loss.

---

## L2-141: Error pages and graceful degradation
**Traces to:** L1-023

Users must see helpful states when something fails, and failures must stay contained.

**Acceptance Criteria:**
1. Given a 404, 403, 410, 429 or 500 response for a page, when it is shown, then a branded error page
   explains what happened in plain language and offers a next step, and the correct HTTP status is
   returned.
2. Given the video processing, search or email service is unavailable, when users use the rest of the
   platform, then unaffected features keep working, and the affected feature shows an inline error state.
3. Given the search service is unavailable, when a user searches, then the catalogue still loads from
   the database, with a notice that search is temporarily limited.
4. Given the user's network drops, when they try an action, then they see an offline notice, and the
   action can be retried when the connection returns.

## L2-142: Server-rendered public pages
**Traces to:** L1-024

Public pages must be readable by search engines and must render meaningful content before
JavaScript runs.

**Acceptance Criteria:**
1. Given a public page (home, catalogue, topic, expert, course, module, video, article, collection,
   event, certificate verification), when it is fetched without executing JavaScript, then the initial
   HTML contains its title, main heading, summary and primary content.
2. Given a server-rendered page, when it hydrates in the browser, then there is no visible content
   change or layout shift.
3. Given an authenticated-only page (dashboard, studio, admin, messages), when it is requested, then it
   is not server-rendered with personal data, and it returns `X-Robots-Tag: noindex`.

## L2-143: Page metadata and social previews
**Traces to:** L1-024

Every public page must have complete metadata for search and sharing.

**Acceptance Criteria:**
1. Given a public page, when its HTML is inspected, then it has a unique `<title>` (60 characters or
   fewer), a meta description (155 characters or fewer, from the item's summary), and a canonical URL.
2. Given a public page, when it is shared, then Open Graph (`og:title`, `og:description`, `og:image` at
   1200x630, `og:url`, `og:type`) and Twitter card (`summary_large_image`) tags are present, and the
   preview renders correctly in the LinkedIn, Facebook and Slack validators.
3. Given content without a cover image, when the social image is generated, then a branded image
   with the title and type is produced automatically.

## L2-144: Structured data
**Traces to:** L1-024

Public pages must provide schema.org structured data.

**Acceptance Criteria:**
1. Given course, video, article, event and expert pages, when they are inspected, then they contain
   valid JSON-LD for `Course`, `VideoObject`, `Article`, `Event` and `Person`, respectively, and
   `BreadcrumbList` on every page below the home page.
2. Given the Google Rich Results Test, when it validates each page type, then it reports no errors.
3. Given the home page, when it is inspected, then it contains `Organization` and `WebSite` JSON-LD,
   with a `SearchAction` for site search.

## L2-145: Sitemap, robots and indexing control
**Traces to:** L1-024

Search engines must be guided to public content and kept away from everything else.

**Acceptance Criteria:**
1. Given published public content, when `/sitemap.xml` is requested, then it lists every public URL with
   `lastmod`, split into sitemap indexes of at most 50,000 URLs, and it updates within 1 hour of a
   publish or archive.
2. Given `/robots.txt`, when it is requested, then it disallows `/dashboard`, `/studio`, `/admin`,
   `/moderation`, `/messages` and `/api`, and it references the sitemap.
3. Given a non-production environment, when any page is requested, then it returns
   `X-Robots-Tag: noindex, nofollow` and requires authentication.

## L2-146: Stable URLs and redirects
**Traces to:** L1-024

Public URLs must be stable and human-readable.

**Acceptance Criteria:**
1. Given a published item whose title changes, when its new slug is published, then the old URL
   redirects permanently (301) to the new one, and redirect chains never exceed one hop.
2. Given any URL with a trailing slash or upper-case characters, when it is requested, then it redirects
   (301) to the canonical lower-case form without a trailing slash.
3. Given a public URL, when it is generated, then it follows the patterns `/courses/{slug}`,
   `/modules/{slug}`, `/videos/{slug}`, `/articles/{slug}`, `/collections/{slug}`, `/events/{slug}`,
   `/experts/{slug}` and `/topics/{slug}`.

## L2-147: Externalized UI text
**Traces to:** L1-025

All user-facing text must be externalized so that it can be translated.

**Acceptance Criteria:**
1. Given the front end and the email templates, when they are built, then every user-facing string
   (labels, messages, errors, accessible names, page titles, email copy) comes from translation resource
   files keyed by message ID, with en-CA as the source locale.
2. Given a pseudo-locale build (for example accented and 30% longer strings), when the Playwright suite
   runs against it, then every visible string is pseudo-localized, which shows that none is hard-coded.
3. Given messages with counts or variables, when they are written, then they use ICU message format
   with plural rules, never string concatenation.
4. Given API error responses, when they are returned, then they carry a stable error code that the
   front end maps to translated text, and the API's English message is used only as a fallback.

## L2-148: Locale-aware formatting
**Traces to:** L1-025

Dates, times, numbers and durations must be formatted for the user's locale.

**Acceptance Criteria:**
1. Given the en-CA locale, when dates are shown, then they use the format "October 11, 2026" for long
   dates and the locale's short form elsewhere, using the platform's locale formatting, never
   hand-built strings.
2. Given numbers and percentages, when they are shown, then they use the locale's grouping and decimal
   separators.
3. Given the locale is switched to a test locale (fr-CA), when pages render, then dates, numbers and
   times change format with no code change.

---

## L2-149: Language tagging
**Traces to:** L1-025

Pages and content must declare their language.

**Acceptance Criteria:**
1. Given any page, when it renders, then the `html` element has `lang="en-CA"` (or the active locale).
2. Given content, when it is stored, then it records its language (default `en`), and a passage marked
   as another language by the author (for example a Greek or Hebrew word, or a Latin phrase) is
   rendered with the matching `lang` attribute.
3. Given caption tracks and transcripts, when they are stored, then they record their language.

---

## L2-150: Layout robustness for translation
**Traces to:** L1-025

Layouts must accommodate longer translated text.

**Acceptance Criteria:**
1. Given the pseudo-locale build with strings 30% longer, when every page is viewed at XS and XL, then no
   text is clipped, overlapped or truncated without an accessible way to read the full text.
2. Given buttons, tabs and navigation items, when their labels grow, then they wrap or reflow rather
   than overflow their container.
