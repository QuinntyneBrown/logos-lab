# Writing the mocks

The mocks are the product on disk before it exists: one HTML file per screen per state, all built from the
design system's classes. If the repository has the `writing-html-mocks` skill, its rules also apply; this
file is the self-contained version for the Banaro kit.

```
docs/mocks/
  README.md                         cast and catalog, open questions, coverage matrix (generated block)
  index.html                        gallery of every screen and state (generated by check_mocks.py --write)
  manifest.json                     every screen, its states and requirement IDs
  assets/tokens.css, ui.css         @import shims into docs/design-system (written by seed_kit.py; never edit)
  assets/mock.css, mock.js          mock chrome: the floating mock bar, ?theme=, ?chrome=0, the t key
  assets/photos/                    cast photographs
  pages/<id>/<state>.html
  dialogs/<id>/<state>.html
  notifications/<id>/<state>.html
```

## 1. Inventory → manifest.json

List every page, dialog and notification the product has, using the requirements if they exist and the
user's description if not. Add the screens every product has:

- sign in and sign up
- forgot and reset password
- account or settings
- not found (404), forbidden (403), server error (500)
- offline

```json
{
  "project": "Tally",
  "screens": [
    { "id": "today", "kind": "page", "title": "Today", "route": "/today",
      "requirements": ["L2-003"], "states": ["default", "loading", "empty", "error"],
      "not_applicable": {} },
    { "id": "delete-list", "kind": "dialog", "title": "Delete list", "opens_from": "lists",
      "requirements": ["L2-011"], "states": ["default", "busy", "invalid", "failed"], "not_applicable": {} },
    { "id": "toast", "kind": "notification", "title": "Toast", "opens_from": "today",
      "requirements": [], "states": ["info", "success", "warning", "danger", "with-action"], "not_applicable": {} }
  ]
}
```

**States**: theme and width are never separate files. Each kind has required states:

- **Pages** need `default`, `loading`, `empty` and `error`. Add `no-results`, `partial`, `invalid`,
  `submitting`, `success`, `forbidden`, `offline`, `long`, `selected` and `read-only` wherever they can
  happen.
- **Dialogs** need `default`, `busy` and `invalid`. Add `failed`, `confirm`, `success` and `scroll` where
  they apply.
- **Notifications** need `info`, `success`, `warning` and `danger`. Add `with-action`, `stacked`,
  `persistent` and `unread/read/empty` where they apply.

A required state that truly cannot happen goes in `not_applicable` with a reason. Expect 60–250 files for a
real product.

## 2. Cast and catalog (top of README.md)

Before writing screens, write the app's fictional cast and data:

- the signed-in person, with a portrait from `assets/photos/` (the kit portraits may be reused under new names)
- 5–10 other people
- the real objects of the domain (lists, tasks, courses, invoices)
- counts and dates, including "today"

Every mock reuses the same cast and numbers. Use real copy only: no lorem, "Item 1", TODO or placeholders.

## 3. Write each screen

Start from the skill's `assets/templates/`:

| Template | Use |
|---|---|
| `page.html` | signed-out or marketing page: top bar with sign-in, footer |
| `app-page.html` | signed-in page: top bar with icon buttons and account, page head |
| `dialog.html` | a dialog over its page (the page behind is `inert`) |
| `notification.html` | a toast or banner on its page |

Replace every `{{…}}` placeholder and keep the head exactly as the template has it:

- the doctype, `lang`, charset, viewport and `<title>`
- `mock:kind`, `mock:screen` and `mock:state` metas that match the path, plus `mock:requirements` and
  `description`
- the stylesheets `../../assets/tokens.css`, `../../assets/ui.css` and `../../assets/mock.css`, then
  `mock.js` at the end of the body

Each file has a skip link, one `<main id="main">`, exactly one `<h1>` and the `.mock-bar` that links its
sibling states.

Write the `default` state first, then derive the other states by copying it and changing only what differs:

- **loading**: layout-matching skeletons with `aria-busy`
- **empty**: an `.empty` block with one next step
- **error**: keep the chrome, show the error with a way forward
- **invalid**: a `.form-summary` plus field errors
- **busy**: a primary button with `aria-busy` and a spinner

Use **only design-system classes.** When a screen needs something new, add it to the design system first
(`adding-components.md`). Layout uses `.wrap`, `.stack`, `.cluster`, `.grid`, `.two-col`, `.split` and
`.sidebar-layout`. Small one-off spacing may use `style="margin-top: var(--space-6)"` with a token, never a
raw value.

## 4. Check, gallery, screenshots

```sh
python <skill>/scripts/check_mocks.py docs/mocks --write     # validates and writes index.html + README coverage
python <skill>/scripts/screenshot_mocks.py docs/mocks        # 360/768/1280 × light/dark into docs/mocks/.cache/
```

`check_mocks.py` checks:

- the manifest against the files, so there are no missing or orphaned states
- the metas against each path, plus one `h1`, `main`, labels, accessible names, alt text, links and fragments
- for placeholder text

Fix everything, then review the screenshots with the per-mock checklist below and `look-and-feel.md`.

## Per-mock review checklist

- [ ] One primary action. The eye lands on the title, then the key numbers, then the action.
- [ ] Copy and data are real and match the cast.
- [ ] The loading state uses layout-matching skeletons. The error state keeps the chrome and offers a way forward.
- [ ] The empty state explains and offers one next step.
- [ ] Forms have labels, help, inline errors, a summary, `aria-invalid`, `aria-describedby` and a busy state.
- [ ] Dialogs have `role="dialog"`, `aria-modal`, `aria-labelledby`, an inert page behind, a close button and Escape. They become a bottom sheet under 640px.
- [ ] Toasts sit in a live region, are dismissible and offer Undo when the action is reversible. Errors persist.
- [ ] Works at 360, 768 and 1280px with no horizontal scroll (tables scroll inside `.table-wrap`).
- [ ] Light and dark both look intentional.
- [ ] Keyboard order is sensible and focus is visible. Hover-only affordances also show on focus and touch.
